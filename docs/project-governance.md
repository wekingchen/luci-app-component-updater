# 项目知识治理与开发约束

**状态：生效（2026-11-20）** · 适用于 `wekingchen/luci-app-component-updater` 的 `main` 以及后续 PR。

## 为什么分层

| 层级 | 文件或页面 | 作用与优先级 |
| --- | --- | --- |
| 代码事实 | `luci-app-component-updater/`、`tools/`、`components/`、`tests/`、`.github/workflows/` | 实际行为，以运行与可复现测试为准 |
| 项目规则 | `AGENTS.md`、本文件、`docs/acceptance-gates.md` | 要求 AI/人类开发遵守的变更、验证和发布边界 |
| 证据记录 | `docs/ax6s-apk-compatibility.md`、`docs/ax6s-hardware-acceptance-checklist.md`、其他 `docs/` | 已验证与未验证明确分开，保留测试证据 |
| 阅读门户 | `wiki-src/*.md` → GitHub Wiki | 对用户友好的中文产品说明；可同步但不取代可审计事实 |

**不能把“写在 AGENTS.md 里”当作自动强制执行。** 开发助手可能没有读到此文件；关键规则必须由测试或 PR 评审补充约束。Wiki 编辑页面不能直接改写主仓库中的验收结果。

## 兼容性模型

- 包管理器：**opkg/IPK** 与 **APK/APKv3** 两类，并不等于支持它们所有固件版本或所有硬件。
- IPK：GL-MT3600BE 与 N1 继续使用 opkg 路线，隔离 rootfs 覆盖 OpenWrt 21.02.5/24.10.5。**V0.5.6 的 Stable 硬件验收目标仅是 MT3600BE 与指定固件 AX6S，N1 不要求真机测试。**MT3600BE 正常 IPK 更新/回滚由用户明确确认，但完整三阶段终端日志尚未归档；不得虚构原始数据。
- APK：V0.5.0 RC1 仅针对被验证固件镜像的 **AX6S/MT7622 aarch64_cortex-a53**。真实 ARM64 chroot 及包数据库可验证 APK 的离线安装、配置、回滚；2026-11-21 已取得实体 AX6S 的管理器自升级/回滚与 NaiveProxy 正常 APK 升级/回滚证据，但**运行时流量、故障及断电恢复等完整硬件门禁尚未通过**。
- 不得由“APKv3 格式支持”推出“其他 APK 固件的设备也通过验证”。检测不到证据必须拒绝安装，并提供只读诊断。
- 当前首个组件 NaiveProxy；新增其它组件必须单独新增定义、包文件归属分析、依赖、版本、恢复包和测试，不得把它们凭空称为可更新。

## 必须保护的功能

- 仅授权的固定组件更新；不更新内核/固件；不执行任意远程 Shell。
- 固定包文件归属、受限平台与架构；更新预案有效期、安装前备份、SHA256、事务锁及故障回滚。
- 用户 UCI/下载代理设置不被覆写；APKv3 的 `/etc/apk/world` 安装前后语义及原始内容保存。
- 不主动重启 PassWall，也不承诺维护脚本或下一次进程重启绝不会产生短暂影响。
- 无独立签名：GitHub Release API digest / manifest / 包摘要用于完整性校验，不等于防止发布账号或 API 代理被攻陷。
- 管理器 IPK 与 APK 同版本同 Release；组件 IPK/APK 可接力构建，发布按各自验收门禁执行。
- 中文交互，手机与桌面均可操作；危险动作需用户确认、恢复通道存在。

## 验收证据等级

| 等级 | 可宣称的内容 | 不得据此宣称 |
| --- | --- | --- |
| L0：静态检查/单测 | 语法、合约、模拟异常案例通过 | 真实包管理器可安装 |
| L1：真实软件环境 CI | 原生 opkg/APK、指定 rootfs/ARM64 chroot 的安装回滚通过 | 路由器真实闪存和网络无风险 |
| L2：实体设备只读/界面 | 对应设备提供的诊断和桌面/手机 UI 记录 | 写入/回滚已经通过 |
| L3：实体设备安装与回滚 | 指定设备正常安装、配置、手动回滚的实际输出或用户明确确认，且标注证据来源/缺口 | 运行时 PassWall 无中断、故障/断电或其他机型已验证 |
| L4：限定范围稳定版 | 本次列入验收的设备完成正常主流程，双包 CI 通过，保留恢复路径且完整披露未测情形 | N1 真机、异常断电/在线服务等未测路径已通过 |

当某设备只达到 L1 时，Release 必须写 **RC / prerelease，实体设备未验收**。原始证据在 `docs/`，不能只保存口头结论。

## AX6S 后续自动发布门禁

`AX6S_APK_AUTO_PUBLISH` 在 AX6S 运行中网络与故障/断电等门禁完成之前保持关闭。V0.5.6 的限定设备 Stable 可按用户已确认的范围一次性**人工发布**，不改变通用自动发布流程、不会给后续版本授权；必须使用同一成功 main CI 的双格式产物，SHA256SUMS、不可变标签和设备适用范围均明确。N1 不构成 Stable 的强制真机门槛。

## PR 与发布检查

1. 说明对包管理器、目标机型、依赖、安装/回滚、安全校验、中文 UI、RPC 的影响范围。
2. 增加/更新自动化测试；如果当前无法完成实体设备测试，明确在待办文件记录并阻止稳定版晋升。
3. 运行 `tools/check_docs.py`、Python unittest 和适用的 CI 工作流；检查所有相关工作流结论及差异。
4. 同步 README 与 `wiki-src/` 中受影响章节；Wiki 发布失败不得掩盖主仓库文档构建失败。
5. 版本提升时验证 Makefile、IPK/APK 打包、CI 发布文件名、Release 标签和回归测试同步；不得偷偷覆盖既有 Release。
6. 仅在获得用户确认时合并或发布可能影响真机使用的新行为；合并后审查分支清理、Release 产物及 SHA256。

## Wiki 自动同步

主仓库的 `wiki-src/` 是**唯一允许机器同步到 GitHub Wiki 的页面源**。`tools/check_docs.py` 验证页面和内部链接；`.github/workflows/wiki-publish.yml` 只在可信 `main` 推送时同步，不从 PR/fork 读取推送密钥，也不强推 Wiki 历史。

Wiki 是独立的 `<owner>/<repo>.wiki.git` 仓库，第一次需要 GitHub 初始化首页；如果 GitHub Actions 默认令牌没有 Wiki 写权限，需要在仓库设置中配置专用 `WIKI_PUSH_TOKEN`（只授予所需写入范围，**不能提交进代码**）。同步受阻时文档仍在主仓库，以 CI 状态和日志为准；不应假装 Wiki 已发布。

## 维护策略

- 每新增一个组件、固件族或适配器，都更新兼容性矩阵与风险清单，并补充对应代码测试。
- 拆除或降级功能必须保留迁移说明，不得使安装过旧版的设备失去恢复能力。
- 旧版本记录可归档，入口页只表达当前能力，不用过期版本说明替代现状。
- `docs/ax6s-hardware-acceptance-checklist.md` 保持待办状态直至每项真实验收有记录。
