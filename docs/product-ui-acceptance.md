## 设计与可读性验收标准

- **最低对比度**：正常正文、状态、操作按钮（包括禁用态的解释性文字）在对应背景上的对比度目标至少 4.5:1；不能仅靠不同颜色表示状态。单测计算主要颜色对比度，但对嵌入式 LuCI 主题的最终效果仍需真实浏览器检查。
- **主题隔离**：宿主 GL.iNet LuCI 给 `h2/h3`、`section`、`header`、`cbi-map` 的背景或伪元素可能造成白色遮挡与蓝色装饰条。组件应在本身命名空间内修复，不修改平台导航、其它 LuCI 页面与原生系统菜单；页面宽度不能横向溢出。
- **响应式**：320、360、375、390、430、768、1280px 检查，无横向溢出，标题完整，状态标签不折行，数字版本可换行，按钮至少 44px 高，Safari Safari 底部控件不遮挡操作。
- **紧凑且有层次**：主页面依次是标题/状态、NaiveProxy 版本与下一步操作、设备摘要、可展开的诊断。设备摘要最多四行，固件平台、进程和构建细节移入诊断，不用大面积炫光、渐变堆叠与重复标题。
- **操作逻辑**：未检查/无候选时突出「检查官方更新」；发现适配候选并完成计划校验后才突出「下载并更新」；确认已是最新版时将「重新检查更新」变为普通可选操作，不提示需要首次检查。没有本机恢复包时「恢复上一个版本」不可点击，也不能用 JS 直接打开恢复确认弹窗。
- **功能边界**：更新中三按钮禁用，危险操作二次确认；尚未适配的 APK 固件禁止写入；失败需提示中文；不同格式仍通过各自原生安装器恢复，不会主动重启 PassWall。
- **下载设置**：系统菜单隐藏单独的设置子菜单，但原设置 URL 仍可通过首页‘下载设置’打开。任何模式下都显示预设节点；关闭中转时它仅作为预存设置、不应生效。仅在中转模式显示‘失败时尝试直连’，仅自定义中转时显示 HTTPS 地址。表单保存不改原有 UCI 配置语义；反代只改变传输通路，不改变来源和校验。
- **资源与缓存**：本地 CSS 携带版本查询参数，避免真实路由器升级后 Safari 复用 V0.5.0 旧样式；无第三方字体、图标库与 CDN。

## 2026-11-20 AX6S 更新检查失败的真实设备反馈

- 用户报告 AX6S 已恢复正常互联网连接，但 LuCI「检查官方更新」先出现“检查未通过/暂时无法更新”，随后短暂显示“更新进行中/正在处理更新任务”，说明文字却写“当前没有正在执行的任务”。这仅能说明 UI 显示了错误/矛盾状态，**尚无设备后端 check-state 原始消息，不能声称已找到真实检查失败的根因**。
- 源码确认 `operationBusy` 同时用于正在检查和正在安装，导致 `job_state=idle` 时错误显示“更新进行中”；V0.5.5 候选用 `operationKind=check` 显式区分检查与更新。另一方面，RPC 返回缺少 `status` 或 `unsupported` 时不再提示“操作已提交”。
- AX6S APK 检查此前把下载校验清单失败和 SHA256 不匹配合并返回“APK manifest hash mismatch”，现已拆为传输失败和摘要不匹配两个不同失败条件，均保留原先的严格 SHA256 拒绝策略。新增 APK 检查失败原因中文映射及 Node/Python 回归。
- 实机定位需只读查看 `/usr/sbin/component-updaterctl status` 和 `/tmp/component-updater/check-state.json`，确认具体失败阶段、下载设置/固件基线与回滚状态；不能把“能上网”直接推导为“官方 GitHub API 和 Release 文件均可达”。
- 以上修复不改变 NaiveProxy 安装许可、包摘要算法、原厂基线哈希、APK world/恢复策略，亦不放宽对未知设备的写入限制。实机最终检查成功与安装/恢复仍未验收。

- 本轮诊断修复产生与早期 V0.5.5-r1 不同的二进制，因此管理器包发布编号提升到 **V0.5.5-r2**（SDK IPK 0.5.5-2、APKv3 0.5.5-r2）；保持独立候选，不覆盖先前构建文件。

## AX6S Overlay 空间预算（V0.5.5-r3，2026-11-20）

- 真实设备：`/tmp` tmpfs 可用 115.9 MiB，`/etc` overlay 可用 12.3 MiB，之前 APK 检查共用 `space_ok()` 的固定 16 MiB overlay 最小值，造成 `Insufficient space for APK backup`，未发出 GitHub 请求。
- r3 仅 APK 路径改为“查询版本 → Release 摘要及资产大小 → 验证下载的 APK → 在 /tmp 解包并核对 ELF SHA256、大小 → 计算持久 overlay 需求 → 生成有效计划”；实际安装前再次验 SHA256、大小和 overlay 空间。保留 IPK 固定预检及所有原有签名/摘要/平台门槛。
- overlay 预算至少包含原始恢复 APK、下一次升级使用的已安装 APK 缓存、候选与旧版 ELF 的较大字节数及 1.5 MiB 文件系统/数据库余量；从未把 tmpfs 的容量算作持久回滚空间。r3 删除从未用于恢复的额外旧 ELF 副本；未来升级时对受验证的活动 APK 创建硬链接，不再重复复制。恢复之前仍验证原始包哈希及 world/config 文件。
- `apk extract` 仅在 tmpfs 对已核验 SHA256 的候选包运行，无脚本安装，不变更持久设备文件。若设备缺少该命令、解包文件/摘要有误、预算仍不足，必须拒绝更新，不能绕过任何保护。
- 测试门禁：模拟 12.3 MiB / 9 MiB 的准入与拒绝；原生 AX6S chroot 下载/安装/回滚完整演练。上述仍不等于实机 Overlay 写入压力或断电回滚验收完成。
